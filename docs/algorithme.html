Documentation · l'algorithme de X décortiqué

Ce qui fait baisser un post sur X.

Ignorer un post, cliquer sur « pas intéressé », masquer, bloquer, signaler : on entend tout et son contraire sur ce qui marche. X a publié le code de son algorithme de recommandation, alors on l'a lu. Voici ce qu'il dit vraiment.

Qui a écrit cette page ? L'analyse a été faite par Claude Code, l'assistant de programmation d'Anthropic. Il a lu le code de X et rédigé cette documentation. Son analyse a ensuite été relue par plusieurs agents Claude indépendants, qui ont confronté chaque affirmation au code. X n'a publié qu'une partie de son algorithme : quand une conclusion dépend de ce qui manque, la page le signale.

Analyse du dépôt xai-org/x-algorithm, version publiée le 28 octobre 2026 (commit 5ed7963). Les liens pointent vers cette version précise.

L'essentiel en 30 secondes

Si vous ne lisez qu'une chose, lisez ce tableau. Le reste de la page explique d'où viennent ces conclusions.

À retenir

Presque tout ce que vous faites agit sur votre fil, et sur celui des gens qui vous ressemblent. Dans le code publié, ignorer, masquer ou bloquer un compte, même par milliers, ne réduit pas la diffusion de ses posts auprès de ses abonnés. X affirme dans un commentaire du code que le classement est pensé pour résister aux blocages et signalements de masse. La vraie exception, c'est la suspension, que peuvent déclencher des classifieurs anti-abus dont certains semblent s'appuyer sur les signalements.

Comment X choisit ce que vous voyez

Chaque fois que vous ouvrez l'onglet « Pour vous », X sélectionne un grand nombre de posts candidats, puis il doit les classer. Pour ça, un modèle d'intelligence artificielle (appelé Phoenix) essaie de deviner ce que vous allez faire avec chaque post :

  • quelle est la probabilité que vous le likiez ?
  • que vous y répondiez ?
  • que vous cliquiez sur « pas intéressé » ?
  • que vous bloquiez son auteur ?
  • que vous le signaliez ?

Chacune de ces probabilités est ensuite multipliée par un poids : positif pour les actions que X veut encourager, négatif pour celles qui montrent que le post vous déplaît. On additionne le tout et on obtient un score. Plus le score est haut, plus le post apparaît haut dans votre fil.

score = P(like) × poids like + P(réponse) × poids réponse + … + P(bloquer) × poids bloquer + P(signaler) × poids signaler

Le calcul se trouve dans xai-value-model/scoring.rs, fonction compute_weighted_score. Le score subit ensuite quelques ajustements, par exemple pour éviter de montrer trop de posts du même auteur.

Le point que presque tout le monde rate

Les poids ne multiplient pas le nombre de blocages ou de signalements qu'un post a reçus. Ils multiplient votre probabilité à vous de faire cette action, prédite à partir de votre comportement passé. X le précise noir sur blanc dans un commentaire du code : il est faux de dire qu'« un signalement annule 468 likes » (scoring.rs, lignes 28 à 56).

Conséquence directe : quand vous bloquez ou masquez quelqu'un, vous apprenez au modèle que vous, et les profils proches du vôtre, réagissez mal à ce genre de contenu. Vous ne retirez pas directement de points au post pour le reste du monde.

Les cinq signaux négatifs et leur poids

Voici les poids négatifs par défaut, tels qu'ils sont écrits dans le code. Plus le nombre est grand (en valeur absolue), plus le signal pèse.

Les poids de home-mixer servent surtout en secours, si vm-ranker ne répond pas, et pour le second tri décrit plus bas (home-mixer/scorers/vm_ranker.rs). vm-ranker a les mêmes poids négatifs, sauf « pas intéressé », fixé à −47,52 (vm-ranker/params.rs). Les deux services déclarent leurs poids sous les mêmes noms de réglage (par exemple rust_home_mixer_not_interested_weight). Une valeur fixée par X en production s'applique donc sans doute aux deux, et les écarts entre valeurs par défaut disparaissent. Le code ne permet pas de le confirmer.

Pourquoi un signalement pèse si lourd ?

Ce n'est pas parce qu'il serait « 7 fois plus grave » qu'un blocage. C'est parce que c'est un geste extrêmement rare. D'après le commentaire du code, la probabilité de base d'un signalement est plus de 1000 fois plus faible que celle d'un like. Sans un poids énorme, une probabilité aussi minuscule n'aurait aucun effet sur le classement.

Un deuxième tri où bloquer et masquer ne comptent pas

Après ce premier score, X peut réordonner la page entière avec un second système (le page decode rerank). Ce système est désactivé par défaut dans le code (EnablePageDecodeRerank = false), mais X peut l'allumer pour une partie des utilisateurs. Pour calculer son score, il ne regarde que trois signaux négatifs : « pas intéressé », signaler et ignorer, avec les mêmes poids que ci-dessus (page_decode_rerank_scorer.rs). Bloquer et masquer n'entrent pas dans ce score.

Ils comptent en revanche dans un mode d'apprentissage de ce système, lui aussi désactivé par défaut : un post qui a reçu un « pas intéressé », un signalement, un blocage, un masquage ou un « montrer moins » ne rapporte aucune récompense au modèle (phoenix/xrex/models/page_rl.py).

Les valeurs réelles peuvent être différentes

Ce sont les valeurs par défaut écrites dans le code. X peut les modifier à tout moment en production, sans republier le code : ce sont des réglages à distance (des feature switches), qui peuvent même différer d'un groupe d'utilisateurs à l'autre pour des tests. vm-ranker prévoit aussi de faire varier légèrement les poids d'un utilisateur à l'autre (WeightPerturbationSigma, à 0 par défaut). Prenez ces chiffres comme des ordres de grandeur, pas comme les valeurs exactes utilisées aujourd'hui.

Ignorer : le signal le plus faible

Une consigne circule souvent : « n'interagissez pas, ignorez leurs posts, l'algorithme comprendra que ce contenu n'intéresse personne ». C'est vrai sur le principe, mais l'effet est minuscule.

Ce qui se passe quand vous ignorez un post

Quand un post s'affiche à l'écran et que vous passez sans vous arrêter, l'application envoie un événement appelé ClientTweetRecapNotDwelled (« post affiché mais pas regardé »). Le modèle apprend à prédire cet événement, ce qui explique qu'il ait son propre poids (constants.py, IsRecapNotDwelled). En principe, un post ignoré est aussi un exemple de « post qui ne vous a pas fait réagir », ce qui doit faire baisser doucement vos probabilités prédites de like ou de réponse sur ce genre de contenu.

Pourquoi ça compte si peu

Parce qu'ignorer est le comportement normal. Vous passez sans vous arrêter sur l'immense majorité des posts de votre fil. Un post ignoré peut vouloir dire « je n'aime pas », mais aussi « je l'ai déjà vu », « je scrollais vite », « je suis pressé ». C'est un signal très bruité, et X lui donne un poids minuscule : −0,02.

Attention à ne pas comparer les poids directement : ils multiplient des probabilités. Ignorer est très probable, cliquer sur « pas intéressé » est très rare, donc l'écart réel entre les deux est bien moindre que l'écart entre leurs poids. Mais « pas intéressé » est un geste volontaire au message clair, et c'est notre déduction qu'il pèse nettement plus qu'un post ignoré. À l'entraînement, X traite d'ailleurs un post ignoré comme un « négatif léger » (recsys_two_tower_model.py).

Un post ignoré ne revient pas de toute façon

Si votre crainte est de revoir le même post encore et encore : X retire déjà de votre fil les posts qu'il vous a montrés. C'est le rôle du filtre PreviouslySeenPostsFilter, appliqué avant le classement (previously_seen_posts_filter.rs). Ce qui revient, ce sont d'autres posts du même auteur ou sur le même sujet.

« Pas intéressé » propose aussi d'agir sur l'auteur

Le menu de retour d'un post propose plusieurs options, dont « Montrer moins de posts de @compte » et « Montrer moins de reposts de @compte ». Chaque retour est envoyé à X avec une durée de vie de 30 jours (home-mixer/util/urt/feedback.rs). Ce « montrer moins » fait partie des retours négatifs que le modèle Phoenix apprend à prédire, au même titre que « pas intéressé », le signalement, le masquage et le blocage (constants.py). En revanche, l'effet direct pendant 30 jours sur les posts de cet auteur est géré par un service qui n'est pas publié.

En pratique

Si un type de contenu vous déplaît, « pas intéressé » est bien plus efficace que l'ignorer. C'est aussi le seul signal négatif volontaire, avec le signalement, que le second tri de la page prend en compte quand il est activé.

Masquer et bloquer : effacer un auteur de votre fil

Au-delà des poids, masquer et bloquer ont un effet beaucoup plus radical : un filtre. Avant même le classement, le filtre AuthorSocialgraphFilter retire tous les posts des comptes que vous avez bloqués ou masqués. Pour les comptes bloqués, il retire aussi les reposts et les citations de leurs posts faits par d'autres. Il retire enfin les posts des comptes qui vous ont bloqué (home-mixer/filters/author_socialgraph_filter.rs).

Pour votre fil, masquer et bloquer reviennent donc au même : l'auteur disparaît, ses posts à venir aussi. Ce n'est pas une baisse de score, c'est une suppression pure et simple.

Masquer

L'auteur disparaît de votre fil. D'après le fonctionnement de l'application (ce n'est pas dans le code), il n'est pas prévenu et peut toujours voir vos posts. Votre masquage sert aussi à entraîner le modèle commun (IsMuteAuthor). Aucun calcul de réputation publié ne l'utilise.

Bloquer

L'auteur disparaît de votre fil, et vous du sien. Votre blocage sert aussi à entraîner le modèle commun (IsBlockAuthor), et il est compté dans un ratio de réputation (voir la section suivante) qu'aucun modèle publié n'utilise.

« Bloquer va à l'encontre de la stratégie » : faux

On lit parfois qu'il ne faut pas bloquer parce que l'algorithme comprendrait juste que vous n'avez pas vu le contenu. Il y a une part de vrai : une fois le compte bloqué, vous ne voyez plus ses posts, donc vous ne pouvez plus les ignorer. Mais le blocage est un retour négatif explicite : il apprend au modèle, sans ambiguïté, que ce contenu vous déplaît, là où un post ignoré n'est qu'un « négatif léger ». Et comme on le verra, les blocages reçus par un compte sont l'une des informations données au classifieur qui note ses réponses.

Au-delà de votre fil : la réputation d'un compte

Tout ce qui précède concerne votre fil. Mais X calcule aussi des scores de réputation par compte, enregistrés sous forme d'instantanés quotidiens, et des règles automatiques collent des étiquettes aux comptes suspects. C'est là que vos gestes peuvent toucher un compte auprès des autres. Comme on va le voir, l'effet est plus limité qu'on le croit.

Le ratio « blocages par like »

Un programme appelé Agatha calcule pour chaque compte le ratio BlocksPerFav : combien de gens l'ont bloqué, comparé au nombre de gens qui l'ont liké (agatha/…/RateBasedLabels.scala). Le calcul est plus subtil qu'il n'y paraît :

  • On compte des personnes, pas des clics. Un fan qui like 50 posts du compte compte pour une seule personne. Quelqu'un qui bloque le compte compte pour un blocage.
  • Seuls les likes de « l'extérieur » comptent. Les likes des gens qui suivent le compte, ou qu'il suit, sont exclus (Favs.scala). L'idée est de mesurer comment réagissent les inconnus, pas la communauté du compte.
  • Sur les 30 derniers jours pour les blocages, les likes et les signalements de spam. Seuls les signalements passés par l'outil AbuseTriageTool sont comptés sur 180 jours.
  • Chaque personne est plafonnée à 100 cibles. Si vous bloquez 10 000 comptes, seuls 100 d'entre eux, tirés au hasard, comptent dans le calcul (LabelUtil.scala, maxTakePerSourceID = 100). Les outils de blocage de masse pèsent donc très peu, Barrage compris.
  • Le score est « lissé ». Pour un compte qui a peu d'interactions, le résultat reste proche du ratio moyen du réseau, pour éviter qu'une poignée de blocages suffise à le condamner.
score = (B + 0,1) ÷ (B + F + 0,1 ÷ ratio moyen du réseau)

B = nombre de personnes qui ont bloqué le compte, F = nombre de personnes extérieures qui l'ont liké. Le ratio moyen du réseau est calculé sur tous les comptes, chacun y pesant au plus 1000 interactions (LabelUtil.scala). Plus F est grand, plus il faut de blocages pour faire bouger le score.

Le code définit aussi une variante, MentionFilteredBlocksPerFav, et une fonction qui compte les gens ayant bloqué ou masqué un compte après avoir été mentionnés par lui (RateBasedLabels.scala, blocksMatch). C'est la seule trace du masquage dans ces calculs. Mais le calcul de cette variante n'est pas dans le code publié, et aucun modèle publié ne l'utilise.

La surprise : ce ratio n'est pas utilisé

En suivant le code jusqu'au bout, on découvre que BlocksPerFav est bien calculé, mais qu'aucun modèle du code publié ne s'en sert :

  • le modèle « à ratios » est entraîné uniquement sur les signalements par like et les signalements de spam par like (RateBasedBuildJob.scala) ;
  • le score de réputation Blink utilise ces mêmes signalements, plus les suspensions pour spam et le contenu adulte (BlinkScoreJobTemplate.scala) ;
  • le graphe des blocages n'est même pas chargé par le programme qui prépare les données d'Agatha (ActiveUserFeaturesJob.scala). Le seul endroit où Blink le mentionne sert à l'exclure pour prédire les signalements (BlinkScoreJobTemplate.scala, lignes 287 à 297).

Autrement dit, dans la partie publiée d'Agatha, ce sont surtout les signalements et les suspensions pour spam qui construisent la mauvaise réputation d'un compte, pas le ratio de blocages.

Deux nuances. D'abord, Agatha charge des « tattles », des signalements internes à X, et il en existe un type TattleType.Block. Il est exclu d'un des graphes (NonLegitTattlesNoBlocksGraphDataLoader.scala) mais pas des tattles légitimes, qui servent notamment à prédire le score de suspension pour spam. Or c'est ce score qui déclenche les étiquettes Agatha décrites plus bas. Le dépôt ne dit pas ce que recouvre exactement ce type. Ensuite, que Blink prenne la peine d'exclure le graphe des blocages laisse penser qu'il existe côté production, même s'il n'est pas chargé dans le code publié.

Ce qui arrive à un compte mal noté

Les scores d'Agatha sont lus par botmaker, un moteur de règles automatiques anti-spam. Quand un score dépasse un seuil, une règle colle une étiquette au compte ou à ses posts. Le système de visibilité lit ensuite ces étiquettes et applique ses propres règles (author_rules.rs), chacune dans des contextes précis (levels.rs, safety_level.rs) :

Elles coupent les notifications d'abonnement et, peut-être, pénalisent dans la recherche. SpamHighRecall fait partie des étiquettes qui retirent un compte des recommandations, avec d'autres : contenu adulte, compte piraté, usurpation d'identité, contenu abusif… (levels.rs, recommandations).

Là où les blocages comptent : le tri des réponses

X utilise son IA Grok pour noter les réponses et repérer le spam. Parmi les informations fournies à Grok sur l'auteur de la réponse figure le nombre de blocages « légitimes » qu'il a reçus dans les dernières 24 heures (grox/core/lm/thread.py, activé dans classifier_reply_ranking.py).

La note de Grok est enregistrée comme score de classement de la réponse. Une note de 0 colle l'étiquette RiskyHighVizReply sur la réponse. Les comptes très influents et les comptes certifiés gris sont exemptés (grox/flows/reply_spam/task_write.py).

C'est le seul endroit du code publié où des blocages reçus peuvent jouer sur la visibilité d'un compte auprès des autres, et seulement pour ses réponses. Plusieurs points restent inconnus : ce qui rend un blocage « légitime », quel poids Grok accorde à ce chiffre, et quel service lit ensuite le score et l'étiquette.

Le levier le plus fort : la suspension

Le service anti-abus peut aussi suspendre des comptes, à partir d'étiquettes produites par des classifieurs (enforcement_user.yaml). Deux de ces classifieurs portent un nom qui évoque les signalements : panda_reports_embedding_v10_rough_spam entraîne une suspension temporaire pour manipulation de la plateforme (ligne 47), cse_reports_embedding une suspension définitive pour exploitation sexuelle de mineurs (enforcement_post.yaml). Le fonctionnement de ces classifieurs n'est pas publié, mais aucune règle de ce service ne lit directement les blocages, les masquages ou les « pas intéressé ».

Pourquoi une campagne coordonnée marche mal

Imaginons que des milliers de personnes se mettent d'accord pour bloquer, masquer ou ignorer un compte. Le code contient plusieurs protections qui limitent fortement l'effet :

  1. Tout est personnalisé

    Les poids s'appliquent à votre probabilité d'agir. D'après X lui-même, dans un commentaire du code, les gestes des militants apprennent surtout au modèle à moins montrer ce contenu… aux militants et aux gens qui leur ressemblent. Le public habituel du compte n'est presque pas touché.

  2. Seul le fil d'accueil compte

    D'après le commentaire de scoring.rs, une action ne compte pour le classement que si elle a lieu sur un post qui vous a été servi dans votre fil d'accueil. Aller chercher le post via un lien partagé dans un groupe n'a aucun effet sur le classement. Attention : cette protection vaut pour le classement seulement. Les calculs de réputation comptent les blocages et les signalements d'où qu'ils viennent.

  3. On compte des personnes, plafonnées

    Dans les calculs de réputation, chaque personne ne compte qu'une fois par compte, et pour 100 comptes au maximum. Les blocages en masse sont dilués.

  4. Les likes extérieurs compensent

    Les ratios divisent par le nombre de personnes extérieures qui likent le compte. Un compte populaire encaisse beaucoup de signalements avant de bouger.

  5. Les signalements sont en partie filtrés

    Pour les signalements de spam, X calcule deux versions : une qui ne garde que les signalements jugés légitimes (legitOnly), une autre qui les garde tous. Les deux sont utilisées (RateBasedLabels.scala). Les autres signalements ne sont retenus que s'ils proviennent de l'outil de traitement des abus (AbuseTriageTool, getReports). Comment X juge un signalement « légitime » n'est pas publié.

  6. Les gros comptes sont exemptés

    Le service anti-abus ignore les comptes au-dessus d'un certain nombre d'abonnés ou d'un certain score de crédibilité (enforcement_user.yaml), sauf pour certains posts où cette exemption peut être levée. Les seuils réels sont cachés : le code publié les remplace par la valeur fictive 12.34, « pour limiter le contournement ». Les règles botmaker d'Agatha exemptent aussi les comptes très influents et les comptes certifiés gris.

Le piège : répondre pour critiquer

Si votre but est de voir moins un contenu, le pire réflexe est d'y répondre ou de le citer, même pour le critiquer. Le modèle prédit seulement si vous allez répondre ou citer. Rien dans le code de classement n'analyse si vous êtes d'accord ou non. La réponse et la citation ont chacune un poids de 5, contre 0,66 pour le like dans home-mixer et 0,5 dans vm-ranker (like et réponse, citation). Si vous et l'auteur vous suivez mutuellement, une réponse à l'un de ses posts originaux reçoit même un bonus de +15.

On peut en déduire que répondre apprend au modèle que ce contenu vous fait réagir, et qu'il risque de vous en montrer davantage. Une citation est en plus visible par vos abonnés.

Pour voir moins un contenu, dans l'ordre

  1. Ne pas répondre, ne pas citer, ne pas republier pour se moquer.
  2. Cliquer sur « pas intéressé » plutôt que simplement l'ignorer.
  3. Masquer ou bloquer pour faire disparaître l'auteur de votre fil.
  4. Signaler uniquement ce qui enfreint vraiment les règles : c'est le signal qui pèse le plus sur la réputation d'un compte, et il est en partie filtré.

Et concrètement, que faire ?

Toute cette analyse se résume en quelques règles pratiques : ne jamais répondre aux comptes adverses, cliquer sur « pas intéressé », citer avec un commentaire plutôt que retweeter, retweeter plutôt que liker, se suivre entre soi… et ce qu'il ne faut surtout pas faire pour ne pas être pris pour du spam.

Le guide pratique

Retrouvez toutes ces règles, expliquées et sourcées, sur une page dédiée : Agir sur X.

Ce qu'on ne sait pas

  • Le code publié n'est pas tout le code. X n'a publié qu'une partie de ses systèmes. Il est possible que BlocksPerFav serve dans un programme interne absent du dépôt. On ne sait pas non plus comment l'étiquette BlinkWorst est attribuée, ni quels services lisent les étiquettes de post AGATHA_SPAM et RiskyHighVizReply ou le score des réponses calculé par Grok.
  • Les valeurs de production sont modifiables. Les poids, les seuils des étiquettes et les seuils d'exemption peuvent être changés sans republier le code.
  • L'effet direct de « montrer moins » n'est pas publié. On voit que le retour est envoyé avec une durée de 30 jours et qu'il sert à entraîner le modèle, pas ce que X fait ensuite sur les posts de l'auteur.
  • Les classifieurs du service anti-abus ne sont pas publiés. On voit les sanctions qu'ils déclenchent, pas ce qu'ils regardent.
  • Les modèles sont des boîtes noires. Le code de Phoenix est publié, mais pas le modèle entraîné. On sait quelles données il reçoit et comment ses prédictions sont combinées, pas ce qu'il a réellement appris.
  • Nous n'avons pas tout lu. Le dépôt est très gros. Un exemple : X enregistre pour chaque post le nombre de blocages et de signalements reçus (block_count, report_count dans phoenix-rankall), mais nous n'avons trouvé aucun code publié qui s'en serve pour classer. Nous n'avons pas vérifié non plus si ces totaux servent ailleurs, comme dans les tendances.
